The CHIP_STATUS byte

The first byte the chip shifts out on every transaction. libtropic reads the mode from it and nothing else. Which bits this model can actually set is read off the code; the captures below are the host meeting each one.

Configuration Object

Erased state is all ones and writes only ever clear bits, so every field is a one-way fuse. The chip obeys i_config & r_config, latched at start-up — the running firmware reads that latch through shared memory, never memory itself. Click a register.

Bit positions below are within the 32-bit register value, which is endianness-independent. The stored bytes are not: unlike everything on the L2 wire, configuration_object.py serialises CO registers big-endian (ENDIANESS = "big"). That only matters if you assemble a register from bytes by hand — which is exactly when it bites.

Memory — what the chip keeps

The model has no address space: each partition is one attribute of the chip object, and "non-volatile" means nothing clears it. Slot counts are read off the UAP registers' field names (gen_ecckey_slot_24_31 ⇒ 32 slots); sizes off the partition modules. I is one-time programmable, R is erasable.

What a reboot clears

L2 request gating

A mode exposes an API surface; a request outside it is not "refused", it is a request the running firmware does not implement — which is why silicon answers UNKNOWN_REQ. The reason column is the comment on each row of the model's own table, read out of the source.

Get_Info objects per mode

The same opcode, answered by two different firmwares. An object a firmware does not serve is absent from its table rather than rejected by a branch.

Get_Info(FW_BANK) — the bank header

Two banks per firmware is what makes a fail-safe update possible: the new image goes to the inactive bank and is only then activated. The header is readable only in Start-up mode, via Get_Info(FW_BANK). The offsets below are derived from the model's own struct format string, so they cannot disagree with what it packs.

L3 commands — inside the secure channel

All of these arrive encrypted inside Encrypted_Cmd_Req, in a session only Handshake_Req can open — and both of those are Application-only above, which is why there is no Start-up column here: in maintenance mode L3 is not refused, it is unreachable. Each command is gated by a Configuration Object register holding one privilege byte per pairing-key slot. Click a command for its fields; try it shows it sent for real, with the L2 frames that carried it and the SPI transactions under those.

Send a request

This follows the chip's current mode — reboot in the Boot tab and the answers here change with it. Every answer is bytes the model really produced — each one captured against a fresh chip put into that mode, so nothing leaks between them. The same request is shown in the other mode alongside, which is the fastest way to see what changes when the bootloader is answering instead of the mutable firmware.

How the code got there

The same request, traced. It was run under Python's tracer and every call into, and return out of, the model's own modules was recorded — file, function, line, and what came back. Step through it like a debugger; the pane on the right shows the source of the function the current step is in. Nothing here is described by hand: the steps are the record, the source is the file.

A scripted session

The same machinery run as a sequence rather than one-off. Determinism is forced — the RNG is pinned and the busy simulation disabled — which is why two handshakes give identical bytes. On silicon that would be alarming; here it is the proof that nothing is floating.

The repository's own examples, executed

These are the scripts in ts-tvl's examples/ directory, run unmodified with the send path instrumented. You get the source, what it printed, and the bytes underneath — not a description of what they do.

Constants

Everything tvl/constants.py exports, read off the module rather than retyped — every enum with its members and their documentation, every size, every encoded version. Click a value to see it in other bases.

Byte order is shown as little-endian because that is the only order L2 uses: the CRC goes out as 2b 92 for a value of 0x922B, the firmware version word is to_bytes(4, "little"), and the FW bank header is struct "<HBB4sII32sI". The one exception in the codebase is not on the wire at all — configuration_object.py stores Configuration Object registers big-endian, so a CO word assembled by hand is the place to get this wrong.

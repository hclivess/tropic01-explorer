L2 request gating

A mode exposes an API surface; a request outside it is not "refused", it is a request the running firmware does not implement — which is why silicon answers UNKNOWN_REQ. The reason column is the comment on each row of the model's own table, read out of the source.

The same opcode, answered by two different firmwares. An object a firmware does not serve is absent from its table rather than rejected by a branch.

Send a request

This follows the chip's current mode — reboot in the Boot tab and the answers here change with it. Every answer is bytes the model really produced — each one captured against a fresh chip put into that mode, so nothing leaks between them. The same request is shown in the other mode alongside, which is the fastest way to see what changes when the bootloader is answering instead of the mutable firmware.

Live model attached

A real model_server is running behind this page. Sending replaces the captured answer with one produced right now — by a chip whose state you are changing as you go. Power off is not a pause: it drops all volatile state, so the session, the buffers and the latched configuration go with it.

A scripted session

The same machinery run as a sequence rather than one-off. Determinism is forced — the RNG is pinned and the busy simulation disabled — which is why two handshakes give identical bytes. On silicon that would be alarming; here it is the proof that nothing is floating.

Firmware bank header

Two banks per firmware is what makes a fail-safe update possible: the new image goes to the inactive bank and is only then activated. The header is readable only in Start-up mode, via Get_Info(FW_BANK). The offsets below are derived from the model's own struct format string, so they cannot disagree with what it packs.
